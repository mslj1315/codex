# 餐饮经营数据导入与确认设计

## 1. 目标与阶段边界

本阶段让 Android App 能将 Excel、CSV 报表和手工补录的经营数据安全写入服务端，并由门店用户确认后形成可用于后续经营诊断的事实版本。

首版不支持报表截图 OCR、不调用 AI、不执行诊断、不接入抖音或收银平台自动同步，也不处理视频素材。截图识别作为下一阶段能力，复用本阶段的导入批次和人工确认模型。

## 2. 环境与部署

开发环境在本机以 Docker Compose 运行 TypeScript API、PostgreSQL 和对象存储模拟服务。Android 开发包访问本机调试 API。

测试环境部署在现有 Linux 云服务器，使用与本机一致的 Docker Compose 服务定义，并配置独立的 `staging` 子域名、HTTPS、数据库和对象存储桶。生产环境在单独的 Compose 项目、数据库、对象存储桶和密钥集合中运行，不与测试环境共享数据。

本阶段不将云服务器 IP、域名、数据库密码、对象存储凭据或模型密钥提交到 Git。它们只通过部署环境变量和受控密钥文件提供。

## 3. 服务端边界

服务端采用 TypeScript HTTP API 和 PostgreSQL。移动端只持有用户登录令牌，不持有数据库凭据、对象存储凭据或任何模型 API Key。

每条业务记录必须绑定企业、门店和创建者。首版建立最小的开发认证上下文：本地固定的演示企业、门店和管理员身份；其接口边界必须预留 `enterpriseId`、`storeId`、`actorId`，以便后续接入正式登录和企业授权时不重写导入数据模型。

## 4. 数据模型

### 导入批次

导入批次记录一次用户操作，包含：批次 ID、企业、门店、发起人、来源类型（`csv`、`xlsx`、`manual`）、原始文件元数据、创建时间、解析状态、报表起止时间、确认状态和确认时间。

原始文件在本机对象存储模拟服务中保存。数据库仅保存文件对象键、原始文件名、MIME 类型、大小和校验值。测试/生产部署时使用相同接口连接对应的私有对象存储桶。

### 指标候选值

每个解析或手工输入的字段创建独立候选值：指标键、显示名、数值、单位、时间范围、来源行/列、置信度、问题原因、确认状态和确认后的值。

首版支持以下经营指标：营业额、订单数、人均消费、套餐售卖数、套餐核销数、退款金额、推广花费。值统一以整数最小单位保存：金额为分、数量为整数、比例为万分比；API 同时返回显示单位，客户端不得自行猜测单位。

### 经营事实版本

当用户确认候选值时，服务端创建新的门店经营事实版本，而不是静默覆盖旧版本。版本记录确认人、确认时间、来源批次和每一个确认指标。后续诊断只能读取确认完成的事实版本。

## 5. 解析与确认工作流

1. 用户选择 CSV/XLSX 或进入手工补录。
2. Android 将文件或手工字段提交到 API，API 创建导入批次。
3. API 用确定性规则读取首张数据表/CSV 表头，将已知列映射为首版指标；未知列保留为未映射信息，不进入事实版本。
4. API 返回导入总览：可直接确认项、待确认项、报表时间范围、单位、字段来源和置信度。
5. 高置信度、单位明确且数值非异常的候选值可被用户批量确认。
6. 缺失、单位不明、时间范围冲突、负值或超出合理范围的候选值必须由用户单项修改或补录。
7. 用户提交确认后，API 校验必填范围和单位，创建事实版本并将批次标记为已确认。

任何未确认、被拒绝或存在问题的候选值不能用于后续正式诊断。客户端必须展示“待确认，尚未用于诊断”而不是把解析结果当作已生效经营数据。

## 6. 置信度与异常规则

首版置信度来自确定性映射，而不是 AI 推理：

- 100：已知标准列名、可解析数值、明确单位和有效时间范围。
- 80：已知别名列名或单位由报表上下文提供。
- 0：缺列、非数值、单位缺失、时间范围缺失、负值不允许或值超出安全范围。

异常规则只负责阻止自动确认，不产生经营结论。金额和数量不得为负；人均消费、订单数和套餐数量不得为零；日期范围起点不得晚于终点。更细的业态阈值和跨周期异常检测留到诊断阶段。

## 7. API 合约

首版 API 提供以下资源：

1. `POST /v1/stores/:storeId/imports/file`：提交 CSV/XLSX 并创建解析批次。
2. `POST /v1/stores/:storeId/imports/manual`：提交手工候选指标并创建批次。
3. `GET /v1/stores/:storeId/imports/:importId`：读取总览和候选值。
4. `PATCH /v1/stores/:storeId/imports/:importId/candidates/:candidateId`：修改一个待确认候选值。
5. `POST /v1/stores/:storeId/imports/:importId/confirm`：确认指定候选值并创建事实版本。
6. `GET /v1/stores/:storeId/facts/latest`：读取最新已确认事实版本。

所有写入接口必须验证演示身份与路径中的企业/门店边界；请求体不得信任客户端传入的企业或创建者身份。

## 8. Android 体验

工作台首页增加“导入经营数据”入口。用户可选择 `Excel/CSV 报表` 或 `手工补录`。

导入完成页采用已确认的总览优先设计：显示来源、报表期间、已识别项数、可批量确认数和待处理项数。用户可先确认全部高置信度字段，再逐项处理异常字段。每项展示字段名、数值、单位、来源、置信度和问题说明。

确认成功后，界面只显示“已生成确认数据版本”，不显示“AI 已分析”或“诊断已完成”。导入历史页显示批次状态；未确认批次可继续编辑，已确认批次只读。

## 9. 测试与验收

1. API 单元测试覆盖列映射、金额/单位换算、置信度、异常拦截和事实版本创建。
2. API 集成测试覆盖 CSV 导入、手工补录、候选修改、确认和企业/门店隔离。
3. Android 单元测试覆盖导入确认状态与 API 请求模型；网络层采用可替换接口，以便本机测试。
4. 使用固定 CSV/XLSX 样本验证已知列、别名列、缺失列、坏日期、负值、单位缺失和未知列。
5. Docker Compose 在全新环境可启动 API、PostgreSQL 和对象存储模拟服务；测试环境使用独立环境变量成功部署。

验收完成时，用户可从 Android 选择一个 CSV/XLSX 或进入手工补录，看到候选指标和待确认问题，确认有效字段后在 API 中读取到带来源、时间范围、单位和确认人记录的最新事实版本。
